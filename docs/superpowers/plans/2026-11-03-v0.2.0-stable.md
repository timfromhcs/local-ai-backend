# Plan: v0.2.0 “stable” across local, GitHub and Vercel

Researched 2026-11-03 (Vercel docs, GitHub Actions marketplace, packaging guides). Rule: every
item ends with a command that proves it, and nothing is marked done because it “should” work.

## What “stable” means here

| Surface | Stable = | Proof |
|---|---|---|
| Local | version is single-sourced, `--doctor` and `--version` work, EXE builds from a clean tree, 100 % of hermetic tests green | `pytest`, `build-exe.ps1`, exe smoke test |
| GitHub | CI runs on every push and PR (Linux + Windows), a tag produces a release with EXE + wheel + checksums, `main` is protected by a ruleset | green Actions run, release page, `gh api` ruleset |
| Vercel | static project pinned to *Other* (no accidental Vite build), production URL public and verified, deploys are reproducible from `web/` | `vercel project inspect`, Playwright check on production |

## Decisions from the research

1. `vercel.json` must set `"framework": null` to force the **Other** preset. Otherwise a project
   created with the Vite preset runs `npm ci` and fails without a `package.json` (this already
   happened once in this repo).
2. Deployment Protection is per project; production stays public because the demo is meant to be
   linkable. Preview URLs may stay protected — CI verification of production is the gate.
3. GitHub Actions (current majors): `actions/checkout@v6`, `actions/setup-python@v7`,
   `actions/upload-artifact@v7`, `actions/download-artifact@v6`, `softprops/action-gh-release@v3`.
   Node 24 runners, Python 3.13, `permissions: contents: write` only on the release job.
4. Releases are cut from tags matching `v*`. The EXE is built on `windows-latest` (PyInstaller is
   not cross-compiled here), the wheel on Linux, and both are uploaded with a SHA256 file.
5. Vercel Git integration cannot be attached to an already-unlinked project through the API, so CI
   deploys through the CLI when a `VERCEL_TOKEN` secret exists and skips honestly otherwise. The
   dashboard “Connect Git” path stays documented for one-click auto-deploy.

## Risks and honest limits

- PyInstaller builds are reproducible only to the extent that the wheel set is pinned; CI installs
  from `pyproject.toml`, so a new transitive release can change the binary. Pinning follows if a
  build ever breaks — not before, to avoid fake stability.
- The browser demo downloads model weights from a CDN; CI checks the page, not the download, so a
  CDN outage is reported by the live page, not by CI.
- No code signing certificate is configured, so Windows SmartScreen will warn on first run. That
  is stated in the README rather than hidden.
