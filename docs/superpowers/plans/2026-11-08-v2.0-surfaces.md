# Plan: LocalAI Gateway v2.0 — every surface, every device, no demos

Research date 2026-11-08. This is the long-form plan the user asked for: SOTA findings first, then
work packages, then the gate that decides whether a package is done. Nothing here is claimed as
done because it was planned.

---

## A. SOTA research (what is actually true, with sources)

### A1. Browser inference
| Runtime | Format | Backend | Weakness that matters here |
|---|---|---|---|
| **wllama** | **GGUF** | WASM, optional WebGPU | single-threaded without COOP/COEP |
| WebLLM | MLC shards | WebGPU | curated catalogue, small default context |
| Transformers.js | ONNX | WebGPU/WASM | heaviest memory (LlamaWeb: +41 % vs wllama) |
| LiteRT-LM.js | `.litertlm` | WebGPU | Gemma family only |

Decision: wllama is the primary browser engine because it runs **the same GGUF files as the local
gateway** and is the smallest footprint. ONNX stays for the embedding/lab path.

### A2. Containers
Vercel runs any `Dockerfile` as a container Function (OCI image, Fluid compute, scale to zero) with
standard Function limits and **no GPU**. Multi-container uses `services` + rewrites. Consequence:
- Vercel container = **API/MCP shell** (auth, routing, persistence of user config), not inference.
- PC/NAS container = **full gateway** (proxy to host llama-server) and can run inference if the host
  passes through `/dev/dri` (Linux) — Windows uses the host binary instead.
- GHCR image is the portable artifact for NAS, Raspberry-Pi-class boxes and CI.

### A3. SAT-based placement
Kissat (CDCL, C) compiles to WASM and runs in browsers (2–3× slower than native). For our problem —
"which models fit which device under constraints" — a full CDCL solver is overkill: the instance is
tiny (≤ 20 models, ≤ 8 constraints). Plan: ship a **deterministic DPLL solver** now (Python + JS,
tested), keep Kissat-WASM as the drop-in upgrade for larger instances. Honest: this is a planner, not
a performance feature.

### A4. Vulkan / CPU auto-tuning
llama.cpp 2026 auto-fits GPU layers, but the *policy* still depends on the device class:
- iGPU (UMA, shared RAM): full offload usually wins, `-ub 256`, threads = physical cores,
  KV q8_0, `--no-mmap` only when RAM is tight.
- dGPU (discrete VRAM): `-ngl 99`, layers = all that fit VRAM with 1 GB headroom, `-t 4..8`.
- CPU-only: `-ngl 0`, threads = physical cores, `-ub 128..256`, small context.
We already measured that kernel env switches (int-dot, fp16, coopmat) give nothing on this RDNA2
iGPU, so the autotuner must not promise them. It selects **policy**, then a benchmark loop keeps the
winner. CPU boost: process priority + power plan are OS-level; only offered as an explicit opt-in.

### A5. Per-user persistence without a server
Local-first options for "each user keeps their own data on their own machine":
- **IndexedDB** (structured, transactional, 100s of MB, works everywhere) → default.
- **OPFS** via SQLite-WASM/PGlite for SQL semantics → later, heavier.
- Export/import JSON so a user can move devices without an account.
Rule: no analytics, no upload, a visible "delete everything" button.

### A6. SEO for a static, private tool page
JSON-LD (`SoftwareApplication` + `FAQPage`), canonical URL, `hreflang` for EN/DE/FR, `sitemap.xml`,
`robots.txt`, per-locale `<title>`/description, semantic headings, and honest content (the page must
not claim speedups we have not measured). Core Web Vitals: no blocking third-party CSS, SVG assets,
`loading="lazy"` below the fold.

## B. Work packages

### WP1 — Placement solver (SAT)
`src/localai_gateway/placement.py`
- CNF builder: one variable per (model, slot), constraints: memory budget, exclusive models,
  at-least-one LLM, kind requirements, pinned models, forbidden pairs.
- DPLL with unit propagation + pure-literal elimination, deterministic ordering, conflict limit.
- `solve_placement(registry, budget_mb, required_kinds=("llm",), pinned=()) -> Placement`.
- Gate: exhaustive test on small instances vs. brute force; property test that no returned placement
  exceeds the budget.

### WP2 — Hardware autotuner
`src/localai_gateway/hardware.py` + `--autotune` in the CLI
- Detect: GPU name, VRAM (or UMA), RAM, physical cores, platform.
- `profile_for(device_class, ram_mb, model_mb)` → flags: `-ngl`, `-t`, `-ub`, `-b`, `-fa`,
  `-ctk/-ctv`, `--no-mmap` decision, plus a human-readable `why`.
- Gate: unit tests for iGPU/dGPU/CPU classes on Windows/Linux fixtures; no benchmark required to pass,
  but the profile must be explainable line by line.

### WP3 — Local-first user data (web)
- IndexedDB store `localai` with `settings`, `chats`, `runs`.
- Save language, tier, last prompts, benchmark runs; "Export JSON", "Import JSON", "Delete all".
- Visible privacy line; nothing leaves the tab.
- Gate: Playwright sets a value, reloads, sees it persisted; export downloads; delete clears.

### WP4 — SEO + i18n completeness
- `sitemap.xml`, `robots.txt`, JSON-LD blocks, canonical, `hreflang` alternates, per-locale meta.
- Gate: `check-web.mjs` validates JSON-LD parses, canonical matches the production URL, every locale
  has title+description, sitemap lists the page, robots allows it.

### WP5 — Containers per device
- `api/Dockerfile` (API shell) — done in v0.3.0.
- `deploy/nas/docker-compose.yml` (gateway + host llama-server, `/dev/dri` example, read-only mounts).
- `deploy/vercel-container/` notes: Vercel container limits, why no GPU, what to deploy there.
- Gate: compose file validates (`docker compose config`), image builds, `/healthz` answers.

### WP6 — MCP surface completion
- Add `placement` and `autotune` tools to `localai-gateway-mcp` (calls the gateway endpoints).
- Gate: MCP probe lists 7 tools, `placement` returns a valid set.

### WP7 — Docs, README, release
- README: surfaces matrix, measured numbers, honest limits, per-device install paths.
- Zero-to-hero extended with: phone install (PWA), container on NAS, autotune step, placement step.
- Release v0.4.0 with the usual artifacts; v1.0 only after two consecutive green release runs.

## C. Order, gates, and the loop

```
WP1 ─┐
WP2 ─┼─► tests green ─► WP3 ─► WP4 (web gate) ─► deploy ─► WP5 ─► WP6 ─► WP7 release
     └─► perf log entry
```

Loop per WP: write the failing test → smallest implementation → run the gate → record the number.
No WP is closed on intent. The release is cut from `main` through the ruleset (PR + required checks).

## D. Honest limits (repeat them in the README)

- Vercel containers cannot run the model; that is a platform fact, not a design choice.
- A phone runs ≤ 1.5B q4 in-browser; 27B stays on the PC.
- Single-threaded WASM without COOP/COEP; enabling those headers breaks CDN imports.
- The DPLL planner is small-instance only; Kissat-WASM is the documented upgrade.
- CPU "boost" is OS priority/power-plan, opt-in, and measurable only by benchmark.
- No code signing; SmartScreen warning stays.

## The hourly loop (requested)

`~/.config/opencode/wake.json` names the session, the directory and the prompt
(`hallo es ist uhrzeit {time} - ... next open point ...`). `scripts/hourly-wake.ps1` posts it via
`opencode run --session <id> --auto`, and `scripts/register-hourly-wake.ps1` registers the Windows
task `OpenCodeHourlyWake` (time trigger + hourly repetition + logon trigger, non-overlapping,
2 h limit). Verified: a real message arrived in the session and `NextRunTime` is populated.

Honest limit: this keeps the *session* working; it does not make the model smarter, and if the
machine sleeps the task runs on wake (`StartWhenAvailable`).
