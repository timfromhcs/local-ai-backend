Local first · OpenAI-compatible · Windows + Vulkan

Your models. Your machine. One API.

LocalAI Gateway puts a single OpenAI-compatible endpoint in front of the models already on your disk. It loads them lazily, keeps the ones that fit, evicts the rest, and routes each request to the cheapest model that can answer it.

Teacher → student, trained in this tab

A frozen ONNX encoder turns each task into a 384-dimension vector. A teacher labels the route (fast / duo / bigout). A softmax head is then trained here with SGD and measured on held-out tasks before and after. That is real training of real weights — of a head, not of the LLM.

Honest scope: WebGPU accelerates inference here. Training the 1–2B model itself happens locally on CPU (LoRA, see the repository) because GGUF is inference-only and browser training of billions of parameters is not viable.

Zero to Hero

Eight steps, in the order that actually works. Each step names the command and what you should see. If a step fails, stop there — every later step assumes the previous one is green.

  1. 1 · Check the machine

    Know your RAM and your GPU before you download 9 GB. Task Manager is not enough; the gateway can tell you.

    localai-gateway --doctor

    You should see your CPU threads, RAM, GPU and a model table with a status per model.

  2. 2 · Put a model on disk

    One GGUF file is enough to start. Keep it next to the exe and list it in models.yaml — the exe ships without weights on purpose.

    models:
  - id: qwen3-4b
    kind: llm
    runtime: llama
    est_mem_mb: 3600
    files: [Qwen3-4B-Q4_K_M.gguf]
    args: ["-c", "16384", "-ngl", "99", "-fa", "on", "--jinja"]

  3. 3 · Start the gateway

    The server starts in under a second because it loads no model until the first request.

    localai-gateway --port 8090
curl http://127.0.0.1:8090/healthz
curl http://127.0.0.1:8090/v1/models

    healthz answers {"status":"ok"}; /v1/models lists every model with a real status.

  4. 4 · First completion

    Any OpenAI client works. Point the base URL at the gateway and use any key — there is no cloud account.

    curl http://127.0.0.1:8090/v1/chat/completions \
  -H "content-type: application/json" \
  -d '{"model":"qwen3-4b","messages":[{"role":"user","content":"hello"}]}'

  5. 5 · Use the duo model

    One virtual model plans with the big model, executes with the fast one, then verifies with the big model. You keep one endpoint and get better tool calls.

    {"model":"duo","messages":[...],"tools":[...]}

  6. 6 · Wire your editor

    Point your coding agent at http://127.0.0.1:8090/v1. Keep the system prompt stable and move volatile context into the first user message — that is what makes the prompt cache work.

  7. 7 · Measure, do not guess

    Record prefill and decode separately. On this laptop decode is bandwidth-bound: 5.9 tok/s for a 27B model at q4 is the ceiling, not a bug.

    llama-bench -m model.gguf -ngl 99 -ub 256
python -m bench.run --gateway http://127.0.0.1:8090 --model qwen3-4b

  8. 8 · Ship it

    Build the single-file exe, copy models.yaml next to it, and keep the weights out of the repository. Then deploy this static page and connect it to your machine.

    powershell -File scripts/build-exe.ps1
vercel deploy --prod web

How the routing works

Requests land on one endpoint. The scheduler checks the RAM budget, starts the model if it is not resident, and holds a refcount so a model is never killed mid-stream. The mode controller picks a lane: fast (small model only), duo (plan, execute, verify) or big-out (small model digests, big model writes). Errors escalate deterministically, so a failing tool call always ends up on the stronger model instead of looping.

  • Explicit CORS origins, never a wildcard
  • Structured errors: model_not_found, does_not_fit, model_unavailable
  • Streaming passthrough with release-on-disconnect
  • Unsupported models are listed with their real error text

Questions people actually ask

Is my prompt leaving my computer?

Not through this page. It is static and has no backend. The in-browser model runs on your GPU or CPU; the local mode talks to 127.0.0.1. The only network traffic is the one-time model download and the CDN assets.

Why ONNX and not GGUF in the browser?

GGUF is an inference format built for llama.cpp. Browsers run ONNX through WebGPU or WebAssembly, so the demo uses ONNX weights. GGUF stays the right choice for the local gateway.

Can I use it with my existing OpenAI SDK?

Yes. Change the base URL to http://127.0.0.1:8090/v1 and keep your code. Streaming, tool calls and the models endpoint are supported.

Does the EXE include the models?

No, deliberately. The exe is the gateway only. Weights live next to it, listed in models.yaml, so updates never re-download gigabytes.

What about AMD and ROCm?

On RDNA2 APUs, ROCm measured roughly six times slower than Vulkan here. The Vulkan path is the supported one; the perf log has the experiment.
